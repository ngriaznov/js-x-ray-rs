# CLAUDE.md

Guidance for agents (and humans) working in this repo.

## What this is

`js-x-ray-rs` is a **behavioral clone** of [`@nodesecure/js-x-ray`](https://github.com/NodeSecure/js-x-ray)
v16, ported line-by-line from TypeScript to Rust. Same probes, same warning
kinds/values/locations, same flags and scores — verified against the
original library's actual output, not against a reimplementation of its
spec from memory.

## Architecture

- **Parser**: [`oxc`](https://oxc.rs) parses JS/TS/JSX and serializes the AST
  to the same ESTree JSON shape meriyah (upstream's parser) produces —
  `Literal` nodes with `value`/`raw`/`regex`, `loc` objects with 1-based
  lines / 0-based columns, etc. (`crates/js-x-ray/src/parser.rs`,
  `crates/js-x-ray/src/estree/`).
- **Everything above the parser operates on `serde_json::Value` trees**,
  exactly like the upstream Node.js code operates on plain ESTree objects.
  This is deliberate: it lets every analysis module stay a near-literal,
  line-by-line mirror of the corresponding upstream file, so porting a new
  upstream change is a mechanical diff-and-translate rather than a redesign.
- **1:1 file mapping**: every Rust module that ports an upstream file starts
  with a `//! Upstream: <path>` doc-comment header naming that file.
  `tools/sync/mapping.tsv` is the authoritative upstream-file → Rust-file
  table (includes files that are deliberately *not* ported — see its
  comments and the README's "Deliberately not ported" section: i18n locale
  bundles and the EventEmitter-style API surface).
- Key modules: `ast_analyser.rs` (entry point, `AstAnalyser::analyse`),
  `variable_tracer.rs` (identifier/require tracing), `deobfuscator.rs` +
  `pipelines/` (deobfuscation passes), `probes/` (one file per detector,
  e.g. `is_unsafe_command.rs`, `crypto/is_weak_algorithm.rs`),
  `obfuscators/` (jsfuck/jjencode/trojan-source/… detectors), `walker/`
  (AST traversal over the `Value` tree).
- `crates/js-x-ray-wasm` is a thin `wasm-bindgen` wrapper exposing
  `analyse(source, optionsJson)`; it depends on `js-x-ray-rs` with
  `default-features = false` (the `fs` feature — `analyse_file`,
  `EntryFilesAnalyser` — is filesystem-only and excluded from WASM builds).

## Running tests

```sh
cargo test --workspace          # everything: unit tests + etalon suite
cargo test -p js-x-ray-rs --test etalon   # just the etalon suite
```

- **Unit tests** (`crates/js-x-ray/tests/*_spec.rs` and friends) are
  transcriptions of upstream's own spec files (walker, estree helpers,
  VariableTracer, Deobfuscator, probes, utils, EntryFilesAnalyser, …) —
  ~430 tests. `cargo test --doc -p js-x-ray-rs` also runs the crate-doc
  example in `lib.rs`.
- **Etalon suite** (`crates/js-x-ray/tests/etalon.rs`) is the real
  cross-check against upstream: it replays every case in
  `tests/etalon/corpus/**.json` through the Rust port and compares the
  result byte-for-byte against `tests/etalon/snapshots/**.json`, which were
  generated by running the *actual* upstream library. Env vars:
  - `ETALON_FILTER=<substring>` — only run matching cases (matched against
    the case's file path).
  - `ETALON_VERBOSE=1` — print full per-case diffs on mismatch.

### Regenerating etalon snapshots

Snapshots are **generated, never hand-written**. After adding or editing a
corpus case, regenerate all of them (deterministic and idempotent — safe to
run any time):

```sh
# needs Node.js >= 24 (upstream requires RegExp.escape); see tools/etalon/README.md
node --experimental-strip-types --disable-warning=ExperimentalWarning \
  tools/etalon/generate.mjs
```

This imports upstream directly from its TypeScript source at
`workspaces/js-x-ray/src/index.ts` in the upstream checkout, runs both
`"code"` and `"file"` corpus cases through it, and writes the reference
JSON. See `tools/etalon/README.md` for the full snapshot format and the
harness's parsing-error/dependency-collection conventions.

Adding a new behavioral test case:

1. Add a corpus JSON under `tests/etalon/corpus/<group>/`:
   `{"name", "code" or "file", "analyserOptions"?, "runtimeOptions"?}`.
2. Run the generator above (regenerates the whole snapshot tree).
3. `cargo test -p js-x-ray-rs --test etalon` must pass for the **whole**
   corpus, not just the new case.
4. If the Rust port disagrees with the freshly generated snapshot, that's
   either a port bug (fix the Rust code minimally and faithfully) or a
   genuine parser divergence (oxc vs. meriyah on some edge case) — in the
   latter case, remove the case rather than weakening an assertion, and
   document it as a known divergence.

## Staying in sync with upstream

The pinned upstream commit/version lives in `UPSTREAM.lock`. To check for
and start a sync:

```sh
tools/sync/pull-upstream.sh
```

This diffs the pinned commit against upstream `HEAD`, maps every changed
upstream file to its Rust counterpart via `tools/sync/mapping.tsv`, and
prints a work list. Workflow: port each diff into its mapped Rust file →
regenerate etalon snapshots → `cargo test --workspace` all green → bump
`commit=`/`version=`/`date=` in `UPSTREAM.lock`.

## Toolchain facts

- CI (`.github/workflows/ci.yml`) pins the toolchain to **1.98.0** (with
  `rustfmt`, `clippy`) and runs `cargo fmt --all --check`,
  `cargo clippy --workspace --all-targets -- -D warnings`, and
  `cargo test --workspace`. A separate `wasm` job builds
  `js-x-ray-wasm` for `wasm32-unknown-unknown` and, as a release-mode
  guard, runs the etalon suite in `--release`.
- `rust-version` (MSRV) is **1.94**, declared at the workspace level
  (`Cargo.toml`).
- Locally, match CI exactly with `rustup run 1.98.0 cargo clippy … / cargo
  fmt …` — a newer default toolchain can produce different (newer) lint
  suggestions than CI enforces.
- Before finishing any change: `cargo fmt --all` and
  `rustup run 1.98.0 cargo clippy --workspace --all-targets -- -D warnings`
  must both be clean.

## Behavioral-clone rules (read before adding analysis code)

- Never hand-author expected output. Every new behavioral test is a corpus
  case anchored to a snapshot generated by *running upstream*, per the
  procedure above.
- When in doubt what upstream does on some input, run it — Node 24 is
  available; upstream is checked out for reference at
  `/home/user/nodesecure/js-x-ray` (or clone it per
  `tools/sync/pull-upstream.sh`).
- Keep the 1:1 file mapping: prefer a line-by-line, structurally faithful
  port over a "more idiomatic" rewrite that drifts from upstream's logic.
  Divergences from upstream structure make future syncs harder to review.
- `serde_json::Value` is the shared AST representation on purpose (see
  Architecture above) — don't introduce a typed AST layer that would break
  the direct correspondence with upstream's ESTree-object code.
